# نظام أتمتة: نشر محتوى فيسبوك / إنستغرام / تيك توك تلقائياً في مدونة Blogger

نظام يعمل عبر **GitHub Actions** على جدولة ثابتة (افتراضياً كل 6 ساعات)، يجلب آخر منشورات
حساباتك الخاصة على فيسبوك وإنستغرام وتيك توك، وينشرها كمقالات جديدة في مدونتك على Blogger،
مع تنسيق HTML نظيف ورابط للمصدر الأصلي، ودون تكرار نفس المنشور مرتين.

> **تنبيه مهم:** هذا النظام يعمل مع **حسابك أنت** فقط (الصفحة/الحساب الذي تملك صلاحياته)،
> لأن واجهات فيسبوك وإنستغرام وتيك توك البرمجية الرسمية لا تسمح بسحب محتوى من حسابات أطراف
> أخرى بدون إذنها الصريح. كما لا يدعم النظام "استخراج منشورات" من WhatsApp Business لأن هذه
> المنصة لا تحتوي على مفهوم "منشورات" أصلاً (هي منصة مراسلة وليست منصة محتوى) — انظر قسم
> "WhatsApp Business" أسفله لبديل مقترح.

---

## 1. ماذا يفعل النظام بالضبط

1. يتصل بـ Facebook Graph API لجلب آخر منشورات صفحتك.
2. يتصل بـ Instagram Graph API لجلب آخر منشورات حسابك (يجب أن يكون حساب Business/Creator
   مرتبطاً بصفحة فيسبوك).
3. يتصل بـ TikTok API لجلب آخر فيديوهاتك (اختياري — يمكن تعطيله إن لم تملك وصولاً).
4. يقارن كل عنصر بملف `state/published_ids.json` لتفادي النشر المكرر.
5. ينشر كل عنصر جديد في مدونتك على Blogger عبر Blogger API v3.
6. يحدّث ملف الحالة ويرفعه تلقائياً إلى المستودع.

كل هذا يعمل بدون أي تدخل بشري **بعد** إتمام خطوات الإعداد الأولية أدناه (وهي خطوة واحدة لمرة
واحدة فقط، لأنها تتطلب تسجيل دخولك الشخصي لإصدار الأذونات — لا منصة في العالم تسمح بتفويض
كامل بدون هذه الخطوة الأولى).

## 2. خطوات الإعداد (لمرة واحدة فقط)

### أ) رفع المشروع إلى GitHub

1. أنشئ مستودعاً جديداً (خاصاً/Private يُفضّل) على GitHub.
2. ارفع جميع ملفات هذا المشروع إليه (`auto_publish.py`, `requirements.txt`,
   `.github/workflows/auto-publish.yml`, `state/published_ids.json`).

### ب) الحصول على Token فيسبوك/إنستغرام

1. اذهب إلى [Meta for Developers](https://developers.facebook.com/) وأنشئ تطبيقاً
   (App Type: Business).
2. أضف منتج **Facebook Login** و **Instagram Graph API**.
3. من [Graph API Explorer](https://developers.facebook.com/tools/explorer/):
   - اختر تطبيقك، واطلب الأذونات: `pages_show_list`, `pages_read_engagement`,
     `instagram_basic`.
   - احصل على User Access Token قصير الأمد، ثم حوّله إلى **Long-Lived Token** (60 يوماً)
     عبر:
     ```
     GET https://graph.facebook.com/v21.0/oauth/access_token?
         grant_type=fb_exchange_token&
         client_id={app-id}&client_secret={app-secret}&
         fb_exchange_token={short-lived-token}
     ```
   - ثم احصل على **Page Access Token** دائم (لا ينتهي ما دام التطبيق نشطاً) عبر:
     ```
     GET https://graph.facebook.com/v21.0/me/accounts?access_token={long-lived-user-token}
     ```
     ستجد في النتيجة `access_token` خاصاً بصفحتك — **هذا هو الذي تستخدمه، وهو لا يحتاج تجديداً
     دورياً** طالما لم تُغيّر كلمة مرورك أو تُلغِ صلاحيات التطبيق.
4. احصل على `page_id` من إعدادات صفحتك، و `IG_USER_ID` عبر:
   ```
   GET https://graph.facebook.com/v21.0/{page-id}?fields=instagram_business_account&access_token={page-token}
   ```

### ج) الحصول على Token تيك توك (اختياري)

1. سجّل تطبيقاً على [TikTok for Developers](https://developers.tiktok.com/).
2. فعّل **Content Posting API** / **Display API** واطلب نطاق `video.list`.
3. أتمم تدفق OAuth (login kit) مرة واحدة يدوياً للحصول على `access_token` و `open_id`
   و `refresh_token` الخاصين بحسابك.
4. **ملاحظة:** رمز وصول TikTok قصير الأمد (يوم واحد عادة)، لذا إن أردت استمرارية طويلة
   بدون تدخل يدوي متكرر، ستحتاج لإضافة خطوة تجديد تلقائي عبر `refresh_token` — أخبرني إن
   أردت أن أضيف هذا الجزء للسكربت.

### د) الحصول على بيانات Blogger OAuth

1. من [Google Cloud Console](https://console.cloud.google.com/)، أنشئ مشروعاً وفعّل
   **Blogger API v3**.
2. أنشئ بيانات اعتماد OAuth من نوع **Desktop App** (Client ID + Client Secret).
3. نفّذ تدفق الموافقة مرة واحدة محلياً (أو عبر [OAuth Playground](https://developers.google.com/oauthplayground/))
   لتضمين النطاق `https://www.googleapis.com/auth/blogger`، واحصل على **Refresh Token**
   (هذا الرمز لا ينتهي ما لم تُلغِ الوصول يدوياً — هو مفتاح الأتمتة الدائمة).
4. احصل على `BLOGGER_BLOG_ID` من: لوحة تحكم Blogger → الإعدادات → معرّف المدونة، أو عبر:
   ```
   GET https://www.googleapis.com/blogger/v3/blogs/byurl?url=https://اسم-مدونتك.blogspot.com
   ```

### هـ) إضافة الأسرار (Secrets) في GitHub

في مستودعك على GitHub: **Settings → Secrets and variables → Actions → New repository secret**،
أضف كل واحد من هذه الأسرار بالقيم التي حصلت عليها أعلاه:

| اسم الـ Secret | القيمة |
|---|---|
| `FB_PAGE_ID` | معرّف صفحة فيسبوك |
| `FB_PAGE_ACCESS_TOKEN` | Page Access Token الدائم |
| `IG_USER_ID` | معرّف حساب إنستغرام Business |
| `IG_ACCESS_TOKEN` | عادة نفس Page Access Token |
| `TIKTOK_ACCESS_TOKEN` | (اختياري) |
| `TIKTOK_OPEN_ID` | (اختياري) |
| `BLOGGER_BLOG_ID` | معرّف مدونتك |
| `BLOGGER_CLIENT_ID` | من Google Cloud Console |
| `BLOGGER_CLIENT_SECRET` | من Google Cloud Console |
| `BLOGGER_REFRESH_TOKEN` | Refresh Token الدائم |

### و) التفعيل

بعد إضافة كل الأسرار، اذهب إلى تبويب **Actions** في مستودعك، فعّل الـ Workflow، ويمكنك
تشغيله يدوياً أول مرة عبر زر **Run workflow** للتأكد من عمله، بعدها سيعمل تلقائياً حسب
الجدولة في `.github/workflows/auto-publish.yml` (كل 6 ساعات افتراضياً — عدّل سطر `cron`
لتغيير التكرار).

## 3. WhatsApp Business — البديل المقترح

لا توجد "منشورات" يمكن استخراجها من WhatsApp Business تقنياً. البديل المنطقي هو العكس:
عند نشر مقال جديد في المدونة، يرسل النظام رسالة تلقائية عبر **WhatsApp Business Platform
(Cloud API)** إلى قائمة جهات اتصال مسجّلة (بعد موافقتهم المسبقة — إلزامي حسب سياسات
واتساب/Meta) تحتوي على رابط المقال الجديد.

**تم تنفيذ هذه الميزة الآن** بنسخة مبسّطة: إشعار واتساب لرقمك الشخصي أنت (وليس قائمة
مشتركين) في كل مرة يُنشر فيها مقال جديد، برابط المقال مباشرة.

### إعداد إشعار واتساب

1. من [Meta for Developers](https://developers.facebook.com/)، أضف منتج
   **WhatsApp** لنفس تطبيقك (أو تطبيق جديد).
2. من لوحة WhatsApp → API Setup، ستجد `Phone number ID` جاهزاً للاختبار، ورمز وصول مؤقت.
3. لإنشاء رمز وصول **دائم**: أنشئ System User من إعدادات Business Manager، وأعطه صلاحية
   `whatsapp_business_messaging`، ثم ولّد توكن دائم له.
4. رقمك الشخصي (`WHATSAPP_TO_NUMBER`) يجب أن يكون بصيغة دولية بدون `+` أو مسافات،
   مثال: `2126XXXXXXXX`.
5. **ملاحظة سياسية مهمة**: لإرسال رسالة WhatsApp Business API لأول مرة لرقم لم يبدأ
   محادثة معك خلال 24 ساعة، تحتاج إلى **قالب رسالة معتمد مسبقاً (Message Template)** من
   Meta، وليس نص حر. بما أن هذه الإشعارات ستكون لرقمك الشخصي أنت، أبسط حل هو أن تبدأ
   أنت محادثة واحدة مع رقم عملك على واتساب (ترسل أي رسالة) — هذا يفتح نافذة 24 ساعة، لكنها
   تنتهي بعد يوم. **للاستمرارية الدائمة بدون أي تدخل بشري متكرر**، يلزم إنشاء قالب رسالة
   بسيط (مثل: "تم نشر مقال جديد: {{1}}") واعتماده من Meta (يستغرق عادة ساعات قليلة)،
   وتعديل `send_whatsapp_notification()` في `auto_publish.py` لاستخدام `type: "template"`
   بدل `type: "text"`. أخبرني إن أردت أن أجهّز هذا التعديل مباشرة.
6. أضف الأسرار في GitHub: `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_ACCESS_TOKEN`,
   `WHATSAPP_TO_NUMBER`.

## 4. إعادة الصياغة بأسلوب مدونة احترافي (عبر Claude API)

**تم تنفيذ هذه الميزة**، وهي اختيارية بالكامل عبر متغيّر `ANTHROPIC_API_KEY` — إن تركته
فارغاً، يُنشر النص الأصلي كما هو بدون أي تغيير.

### الحصول على مفتاح Anthropic API

1. أنشئ حساباً على [console.anthropic.com](https://console.anthropic.com/).
2. من قسم **API Keys**، أنشئ مفتاحاً جديداً (يبدأ بـ `sk-ant-...`).
3. هذا المفتاح **مدفوع حسب الاستخدام** (وليس ضمن خطة Claude.ai العادية) — تكلفة إعادة
   صياغة منشور قصير تقريباً أقل من سنت واحد، لكن راجع [أسعار Anthropic](https://www.anthropic.com/pricing)
   لتقدير دقيق حسب حجم استخدامك.
4. أضف المفتاح كـ Secret في GitHub باسم `ANTHROPIC_API_KEY`.

عند توفر المفتاح، يُعاد صياغة كل منشور (عنوان + نص) بأسلوب مدونة فصيح واحترافي **قبل**
نشره في Blogger، مع الحفاظ على المعنى الأصلي وعدم إضافة معلومات غير موجودة في المصدر.

## 5. الفيديو الترويجي التلقائي (صور + نص → Reel/TikTok)

**تم تنفيذ هذه الميزة**، وهي الأكثر تعقيداً وعرضة للتغيّر في كامل المشروع — فعّلها فقط إن
كنت مستعداً لمتابعة سجلات GitHub Actions وتصحيح أي مشكلة قد تظهر من تحديثات المنصات.

### كيف تعمل

1. عند نشر منشور جديد يحتوي صورة، يُبنى فيديو عمودي (1080×1920، 8 ثوانٍ) بتأثير تكبير
   بطيء (Ken Burns) ونص العنوان كطبقة فوق الصورة، باستخدام `ffmpeg`/`moviepy`.
2. يُرفع الفيديو كـ **GitHub Release asset** للحصول على رابط عام مؤقت (الطريقة الأبسط
   للحصول على رابط فيديو عام بدون حساب استضافة إضافي، لأن واجهات فيسبوك/إنستغرام/تيك توك
   الثلاث تتطلب رابط فيديو عاماً وليس رفعاً مباشراً من الـ runner).
3. يُنشر الفيديو كـ:
   - **Instagram Reel** عبر Instagram Graph API (`media_type=REELS`).
   - **فيديو على صفحة فيسبوك** عبر `/{page-id}/videos` (قد يظهر أو لا يظهر في تبويب
     Reels تحديداً حسب خوارزميات فيسبوك — هذا هو الحد الأقصى المتاح عبر الـ API العام
     دون استخدام نقطة `/video_reels` متعددة المراحل الأكثر تعقيداً).
   - **فيديو تيك توك** عبر Content Posting API (`PULL_FROM_URL`).

### التفعيل

1. أضف Repository Variable (وليس Secret، لأنها ليست سرّية) باسم `GENERATE_PROMO_VIDEO`
   بقيمة `true` من: **Settings → Secrets and variables → Actions → Variables**.
2. لا حاجة لإعداد إضافي لرفع الفيديو كـ Release — `GITHUB_TOKEN` و`GITHUB_REPOSITORY`
   متوفران تلقائياً داخل GitHub Actions.

### قيود TikTok التي يجب معرفتها

نشر فيديو **عام (PUBLIC_TO_EVERYONE)** عبر TikTok Content Posting API يتطلب أن يجتاز
تطبيقك **مراجعة Audit من TikTok** (تستغرق أياماً وتتطلب تقديم تفاصيل عن الاستخدام).
قبل اجتياز هذه المراجعة، التطبيقات تستطيع فقط النشر بخصوصية `SELF_ONLY` (يظهر في حساب
تيك توك نفسه فقط، وليس للجمهور). الإعداد الافتراضي في المشروع هو `SELF_ONLY` تحديداً
لهذا السبب — غيّره إلى `PUBLIC_TO_EVERYONE` عبر Secret باسم `TIKTOK_PRIVACY_LEVEL`
فقط بعد اجتياز المراجعة، وإلا ستفشل طلبات النشر.

### قيود إنستغرام/فيسبوك

- يتطلب نشر Reels أن تكون مدة الفيديو ونسبة أبعاده ضمن الحدود المقبولة (التصميم الحالي
  1080×1920 لـ 8 ثوانٍ متوافق مع المتطلبات الحالية لكلتا المنصتين وقت كتابة هذا الدليل،
  لكن هذه الحدود قد تتغيّر من Meta دون إشعار مسبق).
- معالجة الفيديو على خوادم إنستغرام قد تستغرق دقيقة أو أكثر؛ السكربت ينتظر حتى 20 محاولة
  (كل 10 ثوانٍ) قبل التخلي عن محاولة النشر لتلك الدورة.

## 6. حدود يجب معرفتها (بصراحة كاملة)

- **لا ضمان أبدي 100%**: المنصات تُغيّر سياساتها وواجهاتها البرمجية بين الحين والآخر، وأي
  تعديل كبير من فيسبوك/تيك توك قد يتطلب تحديث السكربت.
- **Page Access Token لفيسبوك/إنستغرام** دائم عملياً طالما التطبيق نشط ولم تُلغِ الصلاحية،
  لكن مراجعات Meta الدورية لتطبيقات الأعمال قد تتطلب إعادة تأكيد الصلاحيات أحياناً.
- **توكن TikTok** قصير الأمد نسبياً ويحتاج آلية تجديد — ذكرتها أعلاه كخطوة إضافية اختيارية.
- **فشل أي ميزة من الميزات الثلاث الجديدة (واتساب/إعادة الصياغة/الفيديو) لا يوقف نشر
  المقال في المدونة أبداً** — كل ميزة مبنية لتفشل بصمت وتطبع رسالة خطأ في سجلات
  GitHub Actions فقط، لأن المقال يكون قد نُشر بالفعل في الخطوة التي تسبقها.
- الفيديو الترويجي تحديداً هو الجزء الأكثر عرضة لأعطال مستقبلية لأنه يعتمد على ثلاث
  واجهات برمجية مختلفة معقدة (رفع فيديو، انتظار معالجة، نشر) — راقب سجلات التشغيل
  بانتظام في الأسابيع الأولى بعد التفعيل.

# الجزء الثاني: جمع طلبات العملاء عبر واتساب الذكي + مسودات عروض تجارية

هذا الجزء **منفصل تقنياً** عن الجزء الأول (نشر المدونة) لكنه يشارك نفس المستودع ونفس
بعض الأسرار (Anthropic، واتساب). يحل محل تطبيق WhatsApp Business العادي الذي كنت
تستخدمه، لأن ذلك التطبيق — كما شرحت سابقاً — **لا يملك أي API** يمكن الاتصال به من
الخارج.

## كيف يعمل

```
عميل يرسل رسالة واتساب
        │
        ▼
خادم ويب صغير دائم التشغيل (whatsapp_webhook/)  ← يستقبل الرسالة فوراً
        │
        ▼
Claude يحاور العميل بأسئلة توضيحية قصيرة (بدون أي تسعير أو التزام)
        │
        ▼
عند اكتمال المعلومات → يُحفظ صف جديد في Google Sheet بالحالة "جديد"
        │
        ▼  (مرة يومياً، عبر GitHub Actions)
generate_proposals.py يقرأ الصفوف "جديدة"، يصوغ مسودة عرض تجاري (.docx) لكل واحد
        │
        ▼
رابط المسودة يصلك أنت شخصياً عبر واتساب للمراجعة — لا شيء يُرسل للعميل تلقائياً
```

**نقطة مهمة جداً:** الوكيل لا يُسعّر ولا يَعِد العميل بأي شيء — فقط يجمع المعلومات.
القرار والصياغة النهائية والإرسال للعميل يبقى بيدك بالكامل.

## لماذا يحتاج هذا الجزء استضافة مختلفة عن GitHub Actions؟

GitHub Actions يعمل فقط عند استدعائه (جدولة أو تشغيل يدوي) ثم يتوقف — لا يمكنه الإصغاء
لحظياً لرسائل واتساب الواردة على مدار الساعة. لذلك يحتاج استقبال الرسائل (`whatsapp_webhook/app.py`)
**خادماً يعمل بشكل دائم** وله رابط عام ثابت. أما صياغة العروض (`generate_proposals.py`)
فتبقى تعمل عبر GitHub Actions بشكل مجدول كالجزء الأول تماماً، لأنها لا تحتاج استجابة فورية.

## خطوات الإعداد

### أ) إضافة منتج WhatsApp لنفس تطبيق Meta

1. في نفس تطبيق Meta for Developers الذي أنشأته سابقاً لفيسبوك/إنستغرام، أضف منتج
   **WhatsApp**.
2. من لوحة WhatsApp → API Setup، اربط رقم هاتف عملك (رقم جديد مخصص للعمل، أو رقم
   اختباري توفره ميتا مبدئياً).
3. أنشئ System User دائماً واحصل منه على **Permanent Access Token** بصلاحية
   `whatsapp_business_messaging`، واحتفظ بـ `Phone Number ID`.

### ب) إنشاء Google Sheet ومصادقة Service Account

1. أنشئ Google Sheet جديداً فارغاً (الأعمدة ستُضاف تلقائياً من الكود عند أول تشغيل).
2. من [Google Cloud Console](https://console.cloud.google.com/) → نفس المشروع المستخدم
   لـ Blogger (أو مشروع جديد) → **IAM & Admin → Service Accounts** → أنشئ حساب خدمة
   جديداً.
3. من تبويب **Keys** لهذا الحساب، أنشئ مفتاحاً جديداً من نوع **JSON** وحمّله — هذا الملف
   هو قيمة `GOOGLE_SERVICE_ACCOUNT_JSON` (انسخ محتواه كاملاً كسطر واحد).
4. **مهم:** افتح الـ Google Sheet وشاركه (Share) مع بريد حساب الخدمة الإلكتروني
   (شيء مثل `xxx@xxx.iam.gserviceaccount.com`، تجده في ملف الـ JSON) بصلاحية **محرر/Editor**
   — وإلا لن يستطيع الكود الكتابة فيه.
5. فعّل **Google Sheets API** من مكتبة الـ APIs لنفس المشروع إن لم يكن مفعّلاً.
6. احصل على `GOOGLE_SHEET_ID` من رابط الشيت نفسه (الجزء الطويل بين `/d/` و `/edit`).

### ج) نشر خادم الـ Webhook (الخطوة التي تحتاج استضافة دائمة)

أبسط خيار مجاني لا يحتاج بطاقة بنكية هو **Render.com**:

1. أنشئ حساباً على [render.com](https://render.com) وأربطه بمستودع GitHub الخاص بك.
2. من Render: **New → Web Service** → اختر المستودع → حدد المجلد الفرعي
   `whatsapp_webhook` كـ **Root Directory**.
3. Render سيكتشف تلقائياً `Procfile` ويستخدم `gunicorn app:app`. تأكد أن **Build
   Command** هو `pip install -r requirements.txt`.
4. من تبويب **Environment** في Render، أضف كل المتغيرات التالية:
   `WHATSAPP_VERIFY_TOKEN` (اخترعه أنت بنفسك، أي نص عشوائي)، `WHATSAPP_ACCESS_TOKEN`،
   `WHATSAPP_PHONE_NUMBER_ID`، `ANTHROPIC_API_KEY`، `GOOGLE_SERVICE_ACCOUNT_JSON`،
   `GOOGLE_SHEET_ID`.
5. بعد النشر، سيعطيك Render رابطاً عاماً دائماً مثل
   `https://your-app-name.onrender.com`.
6. ⚠️ **ملاحظة عن الخطة المجانية لـ Render**: الخدمة المجانية "تنام" بعد 15 دقيقة من عدم
   الاستخدام، وتستغرق نحو 30-50 ثانية "لتستيقظ" عند وصول أول رسالة بعد فترة خمول — قد
   يتأخر رد الوكيل على أول رسالة فقط بعد فترة سكون. إن كان هذا غير مقبول لعملك، فكّر
   بترقية لخطة مدفوعة رخيصة (~7$/شهر) تبقي الخدمة مستيقظة دائماً.

### د) ربط رابط Render بـ Webhook في Meta

1. ارجع إلى لوحة WhatsApp في Meta for Developers → **Configuration**.
2. في خانة **Callback URL** ضع: `https://your-app-name.onrender.com/webhook`.
3. في خانة **Verify Token** ضع نفس القيمة التي وضعتها في `WHATSAPP_VERIFY_TOKEN`.
4. اضغط **Verify and Save** — إن نجحت الخطوات أعلاه سيتم التحقق فوراً.
5. من نفس الصفحة، اشترك (Subscribe) في حقل `messages` تحت Webhook Fields.

### هـ) إضافة أسرار جزء العروض في GitHub (لتشغيل `generate_proposals.py`)

في نفس مستودع GitHub، أضف هذه الأسرار الإضافية (بعضها مكرر من الجزء الأول إن كنت
فعّلت ميزة واتساب هناك):
`GOOGLE_SERVICE_ACCOUNT_JSON`, `GOOGLE_SHEET_ID`, `ANTHROPIC_API_KEY`,
`WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_TO_NUMBER`
(رقمك الشخصي — نفسه المستخدم في إشعارات المقالات الجديدة).

### و) الاختبار

1. أرسل رسالة واتساب لرقم عملك من هاتفك الشخصي (رقم آخر غير رقم العمل) تحتوي طلباً
   بسيطاً، مثل: "أريد عرض سعر لـ 50 قطعة من المنتج X".
2. يجب أن يرد الوكيل بسؤال توضيحي أو أكثر.
3. بعد اكتمال المحادثة، تحقق من ظهور صف جديد في Google Sheet.
4. فعّل الـ Workflow `generate-proposals.yml` يدوياً من تبويب Actions، وتحقق من وصول
   رسالة واتساب لك تحتوي رابط مسودة العرض، ومن تغيّر حالة الصف إلى "تمت الصياغة".

## حدود هذا الجزء التي يجب معرفتها

- **"نافذة الـ24 ساعة"**: سياسة واتساب تسمح بالرد الحر على العميل خلال 24 ساعة من آخر
  رسالة أرسلها هو. إن أردت أن يبدأ الوكيل محادثة من تلقاء نفسه (بدون أن يبدأ العميل
  أولاً)، يلزم استخدام قالب رسالة معتمد مسبقاً من Meta — هذا النظام كما بُني يفترض أن
  العميل هو من يبدأ المحادثة دائماً (وهو السيناريو الطبيعي لوكيل استقبال الطلبات).
- **حالة المحادثة مؤقتة في الذاكرة** (`CONVERSATIONS` في `app.py`): إن أعاد Render تشغيل
  الخدمة أثناء محادثة لم تكتمل، يبدأ العميل من جديد. هذا مقبول لحالة الاستخدام هذه، لكن
  إن أردت حلاً أكثر صلابة لاحقاً (حفظ حالة المحادثة في قاعدة بيانات)، أخبرني.
- **التكلفة**: استدعاء Claude API لكل رسالة واردة، بالإضافة لصياغة كل مسودة عرض، كلاهما
  مدفوع حسب الاستخدام من حساب Anthropic الخاص بك — راجع [أسعار Anthropic](https://www.anthropic.com/pricing).
- مسودة العرض **لا تحتوي أي سعر أو التزام مُخترع** بتصميم مقصود — ستجد فيها فراغات مثل
  `[السعر]` لتملأها أنت بنفسك قبل إرسال أي شيء للعميل فعلياً.
